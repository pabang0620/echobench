# VERIFY: things that only a real sandbox or a real install can settle

The build made no calls; the main session ran V4, V5 (first half), V8 and V11 on 2026-11-12 and V10 through a local Claude Code account (results below). The build did not run the plugin's own generation (R2) and did not install EverShop. The code paths for everything below exist; the items need a person to say "go" and to supply credentials. Record each result in the README ("What is not done yet") and delete the matching hedge wording.

Safety for every item: sandbox credentials only. `scripts/verify-sandbox.js` refuses to run unless `ECHOBENCH_ALLOW_SANDBOX=1`, credentials are present and the base URL is exactly a PayPal sandbox host (checked by parsing the URL, not by searching for the word). It appends one JSON line per step to `VERIFY_RESULTS.json` (git-ignored).

Common setup for V1 to V6 and V11: put sandbox credentials in `.env`, make EchoBench reachable from the internet (a tunnel or a small server) and set `PUBLIC_URL` to that address.

Exposure rule for the tunnel: PayPal only needs `POST /hooks/paypal`. Without more, a tunnel also exposes the refund buttons and Apply. So set `ECHOBENCH_ACCESS_TOKEN` to a long random string in `.env` before opening the tunnel. With it, the server answers `401` to every route except `POST /hooks/paypal`. You open the UI once as `<PUBLIC_URL>/?token=<the token>` (it sets a cookie), and scripts send the header `x-echobench-token`. Check before registering the webhook: `curl -i <PUBLIC_URL>/api/status` must say 401 and `curl -i -X POST <PUBLIC_URL>/hooks/paypal -d '{}'` must say 200. The targets reach the lab on `http://127.0.0.1:<PORT>` (not the tunnel), so the token does not get in their way. If the server starts with a non-local `PUBLIC_URL` and no token it prints a warning. The server also refuses to start with credentials and a `PAYPAL_BASE_URL` that is not a PayPal sandbox host.
